# poo#193690 - Wrong openQA jobs referenced in qem-bot inc-approve

## Problem Summary

When a failed openQA job (e.g. t20252358) is cloned as a new job (e.g. t20256065) that passes,
the bot still reports the incident as having failed jobs. The root cause is that
`approver.py:get_jobs()` (line 343) checks **all** job results returned by the dashboard for a
given `settings_id` with `all(self.is_job_acceptable(...) for r in job_results)`. There is **no
deduplication by scenario** — if the dashboard returns both the old failed job and the new passed
clone, the old one blocks approval.

### Root Cause Chain

1. `sub-sync-results` syncs job t20252358 as `{job_id: 20252358, status: "failed"}` to the
   dashboard under `incident_settings={settings_id}`.
2. t20252358 gets cloned to t20256065 (passed). On the next sync, `syncres.py:filter_jobs()`
   (line 68) skips t20252358 (it now has `clone_id`), and t20256065 is synced as
   `{job_id: 20256065, status: "passed"}`.
3. **Both records coexist in the dashboard** under the same `incident_settings`.
4. `approver.py:get_jobs()` calls `GET api/jobs/incident/{settings_id}`, receives both records,
   and `all(...)` fails because the old failed job is still present.
5. `is_job_acceptable()` (line 319) logs `"Found not-ok, not-ignored job"` for the old failed
   job, even though it has been superseded.

### Acceptance Criteria (from ticket)

- **AC1:** qem-bot only references failed openQA jobs which are actually not ok (failed, incomplete, etc.)
- **AC2:** qem-bot still clearly references blocking failures

### Phase 2: Implement the Fix

**Step 2.1 — Add scenario deduplication in `approver.py:get_jobs()`**

- Location: `openqabot/approver.py`, `get_jobs()` method (line 327-343)
- After fetching `job_results` from the dashboard, **deduplicate by scenario**: keep only the
  job with the highest `job_id` for each unique `name` (the `name` field encodes
  `distri-version-flavor-build-testname@arch`, which uniquely identifies a scenario).
- The highest `job_id` is the most recent execution (clones always get a higher ID).

Proposed implementation — add a helper method to `Approver`:

```python
@staticmethod
def _deduplicate_jobs_by_scenario(job_results: list[dict]) -> list[dict]:
    """Keep only the most recent job (highest job_id) per scenario name."""
    latest: dict[str, dict] = {}
    for job in job_results:
        name = job.get("name", "")
        if name not in latest or job["job_id"] > latest[name]["job_id"]:
            latest[name] = job
    return list(latest.values())
```

Then in `get_jobs()`, after the empty-check and before `mark_jobs_as_acceptable_for_submission`:

```python
job_results = self._deduplicate_jobs_by_scenario(job_results)
```

**Step 2.2 — Add debug logging for deduplication**

When deduplication removes jobs, log it at DEBUG level so operators can trace what happened:

```python
original_count = len(job_results)
job_results = self._deduplicate_jobs_by_scenario(job_results)
if len(job_results) < original_count:
    log.debug("Deduplicated %d -> %d jobs for settings %s",
              original_count, len(job_results), job_aggr.id)
```

**Step 2.3 — Decide on edge cases**

- Jobs **without a `name` field** (empty string): group them separately or keep all. Since
  `name` is always present in synced data (`syncres.py:normalize_data` line 44), an empty name
  would indicate a data anomaly — keep all unnamed jobs to avoid hiding real failures.
- Jobs with **different `name` values** (different scenarios under the same `settings_id`): each
  scenario is deduplicated independently, which is correct.

## Alternative Approaches Considered

1. **Fix on dashboard side**: Have `api/jobs/incident/{settings_id}` return only the most recent
   job per scenario. This would be cleaner but requires changes to qem-dashboard (separate repo),
   and the bot should still be defensive.
2. **Mark old jobs as obsolete during sync**: When `filter_jobs()` skips a cloned job, also PATCH
   it as `obsolete: true` in the dashboard. The approver would then skip obsolete jobs. This is
   more complex and still requires the dashboard to support the filter.
3. **Use `clone_id` field in dashboard response**: If the dashboard returned `clone_id` for each
   job, the bot could follow the clone chain. But this field is not currently in the dashboard
   API response for `api/jobs/incident/`.

The chosen approach (deduplication by scenario `name` using highest `job_id`) is:
- Self-contained within qem-bot
- Simple and auditable
- Consistent with how openQA assigns job IDs (monotonically increasing)
- Requires no dashboard changes

## Risks and Mitigations

| Risk | Mitigation |
|------|-----------|
| `name` field not unique per scenario | The `name` field is constructed as `distri-version-flavor-build-test@arch` which is the scenario key; verify in test data |
| Jobs intentionally re-run (not clones) get deduplicated | Intentional re-runs also get higher job IDs; keeping the latest is still correct behavior |
| `name` field missing from dashboard response | Default to `""` grouping; add defensive handling; unlikely since `syncres.py` always sets it |
| Breaking existing behavior for passing jobs | Only deduplication occurs; if all jobs pass, deduplication is a no-op for the `all()` check |
